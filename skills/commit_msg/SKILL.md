# Commit Message & PR Body Generator

작업한 변경사항(diff)을 분석해서 **팀 커밋 규칙에 맞는 커밋 메시지**와 **PR body**를 함께 만든다.
코드 리뷰 평가 축이 드러나도록 구성한다.

## 핵심 원칙

**diff에 근거가 있는 것만 쓴다.**

이 스킬의 목적은 "안 한 일을 그럴듯하게 적는 것"이 아니라, **"실제로 했는데 기록에 안 드러나던 것을 찾아 명시하는 것"**이다.

개발자는 예외 처리, 경계값 검증, 쿼리 최적화를 해놓고도 "오류 수정"이라고만 쓰는 경우가 많다. 그러면 리뷰어에게 그 작업이 보이지 않는다. 이 스킬은 그 간극을 메운다.

리뷰어는 기록과 diff를 **함께** 본다. 근거 없는 서술은 신뢰도를 떨어뜨리므로, 확인되지 않은 항목은 **쓰지 않는다.**

## 커밋 메시지와 PR body의 역할 분담

| | 담는 내용 |
|---|---|
| **커밋 메시지** | 무엇을 바꿨는지. 간결하게. |
| **PR body** | **왜 필요했는지**, 어떤 이슈에서 출발했는지, 어떻게 검증했는지. |

커밋 메시지에 긴 배경을 욱여넣지 않는다. 상세한 맥락은 PR body의 몫이다.

---

## 팀 커밋 규칙 (준수 필수)

### 기본 형식

```
type: 설명
```

### 타입 (이 8개만 사용)

| 타입 | 용도 |
|---|---|
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서 수정 (README, 주석 등) |
| `style` | 코드 포맷·들여쓰기 등 (동작 변화 없음) |
| `refactor` | 코드 구조 개선 (기능 변화 없음) |
| `perf` | 성능 개선 |
| `test` | 테스트 코드 추가·수정 |
| `chore` | 빌드·설정·패키지 등 기타 잡일 |

> `refactor` 와 `perf` 구분: 성능 향상이 **주목적**이면 `perf`,
> 구조·가독성 개선이 주목적이고 성능은 부수 효과면 `refactor`.

> **`perf` 를 허용하지 않는 프로젝트가 있다.** 타입 목록이 `perf` 를 뺀 7종인 경우,
> 성능 개선은 `refactor` 로 쓰고 개선 사실은 본문과 PR body 에 명시한다.
> 타입을 바꿔 쓴 사실은 사용자에게 알린다.
> 확실하지 않으면 `git log --oneline -30` 으로 `perf:` 가 쓰인 적 있는지 확인한다.

### 작성 원칙

- **제목은 50자 이내.** 무엇을 했는지 명확하게.
  타입·콜론·공백을 포함한 **제목줄 전체** 기준이다. `feat: ` 가 6자를 차지하므로
  설명에 쓸 수 있는 건 44자다. 한글은 바이트가 아니라 글자 수로 센다.
- **한 커밋에는 한 가지 작업만.**
- **무엇을·왜 했는지 드러나게.** "버튼 수정" ✕ → "로그인 버튼 클릭 오류 수정" ○
- **어미를 일관되게.** 명사형(`추가`, `수정`, `제거`)으로 통일.
- **모호한 표현 금지.** `수정`, `일단 커밋`, `오류 고침`, `작업` 같은 제목은 쓰지 않는다.
- 특정 인물을 지목하는 표현은 쓰지 않는다 (`~님이 삭제한` ✕ → `삭제된` ○)

### 요청받은 문장을 그대로 쓰지 않는다

작업 요청을 받은 말투가 그대로 커밋 제목·본문에 실리는 일이 잦다.
요청 메시지나 메모를 근거로 쓸 때는 반드시 **명사형 한 줄로 고쳐서** 넣는다.

- ✕ `이미지 DB 서버 실행 여부만 확인해서 비활성화 되도록 해줘`
- ✕ `DB 서버가 작동되고 있는지 확인해서 생성 폼을 활성화할 수 있나?`
- ○ `이미지 DB 서버 미실행 시 메뉴 비활성화`
- ○ `DB 서버 실행 확인 후 생성 폼 활성화`

요청 원문이 맥락상 필요하면 PR body 의 "왜 필요한가" 쪽에 풀어서 쓴다.

## 실행 순서

### 1. 변경사항 수집

```bash
git status
git diff --staged
git diff
git log --oneline -10
```

- staged 변경이 있으면 그것을 대상으로 한다.
- staged가 비어 있으면 unstaged 전체를 대상으로 하되 사용자에게 알린다.
- 변경량이 크면 `git diff --stat` 으로 개요를 먼저 잡는다.

### 2. 이슈 번호 확인

PR body의 "관련 이슈"를 채우기 위해 아래 순서로 찾는다.

1. **브랜치 이름**에서 추출 — `feat/123-login`, `fix/ISSUE-45` 등
2. **커밋 메시지 이력**에 `#숫자` 가 있는지
3. 위에서 못 찾으면 **사용자에게 묻는다** — "관련 이슈 번호가 있나요? 없으면 비워둡니다."

번호를 모르면 **비워두고 표시만 남긴다.** 임의로 만들어내지 않는다.

### 3. "왜 필요했는지" 파악

PR body의 핵심이다. 아래 순서로 근거를 찾는다.

1. **diff 자체에서 유추** — 조건문 추가, NULL 분기, 쿼리 변경 등에서 어떤 문제가 있었는지 역산
2. **이슈 제목·브랜치명**에서 의도 추출
3. **불명확하면 사용자에게 묻는다**

물을 때는 구체적으로 묻는다.

- "이 수정 전에는 어떤 증상이 있었나요?"
- "어떤 조건에서 재현됐나요?"
- "이 변경이 없으면 어떤 문제가 남나요?"

**추측으로 배경을 지어내지 않는다.** 모르면 빈칸으로 두고 사용자에게 채우도록 안내한다.

### 4. 평가 축별 근거 스캔

diff를 읽으며 아래에 **해당하는 실제 코드 변경이 있는지** 확인한다.
있는 것만 반영하고, 없으면 언급하지 않는다.

| 축 | diff에서 찾을 근거 |
|---|---|
| **security** | 입력 검증 추가, 인증·권한 체크, SQL 파라미터 바인딩, 시크릿·키 처리, XSS/인젝션 방어, 민감정보 로깅 제거 |
| **correctness** | 경계값(월말·연말·0·음수) 처리, NULL 분기, 예외 처리, 오프바이원 수정, 조건문 로직 교정, 타입 변환 |
| **domain_safety** | 도메인 규칙 위반 방지. 의료 시스템이면 환자 식별, 처방·투약 값 검증, 잘못된 데이터 저장 차단, 이력 보존 |
| **performance** | 쿼리 개선(sargable, 인덱스 활용), N+1 제거, 반복문 최적화, 캐싱, 불필요한 조회 제거, 페이징 |
| **readability** | 함수 분리, 네이밍 개선, 중복 제거, 매직넘버 상수화, 주석 추가 |
| **test_coverage** | 테스트 파일 추가·수정, 테스트 케이스 보강. 테스트 코드가 없으면 **수동 검증 방법**을 기술 |

### 5. 난이도 맥락 파악

코드만 봐서는 드러나지 않는 작업 난이도가 있으면 PR body에 넣는다.

- 인수인계 문서 없이 기존 로직을 역추적해야 했던 경우
- 레거시와 신규의 기준이 달라 대조 검증이 필요했던 경우
- 재현 조건을 특정하기 어려웠던 버그
- 영향 범위가 여러 화면·모듈에 걸친 경우

**실제로 그랬을 때만 쓴다.** 확인이 필요하면 사용자에게 물어본다.

### 6. 커밋 메시지 + PR body 생성

둘을 **함께** 출력한다.

---

## 출력 형식 1 — 커밋 메시지

### 단순 변경

한 줄로 충분하면 제목만 쓴다.

```
chore: .gitignore 및 초기 설정 파일 추가
```

### 설명이 필요한 변경

```
type: 한 줄 요약 (50자 이내)

- <변경 내용 1>
- <변경 내용 2>
  -> <그로 인한 결과>
```

본문은 72자 내외에서 줄바꿈. 상세한 배경은 PR body로 넘긴다.

---

## 출력 형식 2 — PR body

```markdown
## 왜 필요한가

<이 변경이 없으면 어떤 문제가 있는지. 어떤 증상이 있었고 왜 고쳐야 했는지.>
<재현 조건이 있으면 함께 기술.>

## 관련 이슈

Closes #<번호>

## 변경 내용

- <무엇을 어떻게 바꿨는지>
- <추가한 처리·분기>

## 검증

- <테스트 코드 추가 여부>
- <수동으로 확인한 방법과 결과>

## 영향 범위

<영향받는 화면·모듈. 리스크가 있으면 함께 명시.>
```

### 섹션별 작성 지침

**왜 필요한가** — 이 PR의 핵심이다. "무엇을 했다"가 아니라 **"이런 문제가 있었다"**로 시작한다.
- ✕ "날짜 필터 로직을 수정했습니다"
- ○ "종료 년/월을 지정해도 조건이 적용되지 않아, 전체 기간이 조회되고 있었습니다"

**관련 이슈** — GitHub 자동 연결 키워드를 쓴다. `Closes #12`, `Fixes #12`, `Resolves #12` 는 PR 머지 시 이슈를 자동으로 닫는다. 단순 참조만 할 때는 `Related to #12` 를 쓴다.
- 이슈 번호를 모르면 `Closes #` 로 비워두고, 사용자에게 채우도록 안내한다.
- 이슈가 없으면 이 섹션을 생략한다.

**변경 내용** — diff에 실제로 있는 것만. 평가 축(security·correctness 등)에 해당하는 처리는 여기서 구체적으로 서술한다.

**검증** — 테스트 코드가 없어도 비워두지 않는다. 수동으로 무엇을 어떻게 확인했는지 적는다.

**영향 범위** — 리뷰어가 어디를 봐야 할지 알려주는 자리. 부작용 가능성이 있으면 솔직히 적는다.

## 예시

### 입력 (diff 요약)
브랜치 `fix/142-period-filter`. 쿼리에서 `YEAR(created_at) = 2026` 형태를 범위 조건으로 변경, NULL 분기 추가, 단위 테스트 파일 추가

### 출력 — 커밋 메시지

```
perf: 기간별 조회 쿼리를 인덱스 활용 가능하도록 개선

- 날짜 조건을 함수 호출에서 범위 비교로 변경
- 종료일이 NULL인 경우 분기 처리 추가
```

### 출력 — PR body

```markdown
## 왜 필요한가

기간별 통계 조회에서 날짜 조건을 `YEAR()` 함수로 감싸고 있어 인덱스를
타지 못했습니다. 조회 기간이 길어질수록 응답 시간이 선형으로 증가했고,
외래·입원을 동시에 조회하면 지연이 특히 컸습니다.

또한 종료일을 지정하지 않은 경우(NULL) 조건이 무시되어 의도하지 않은
전체 기간이 조회되는 문제가 함께 있었습니다.

## 관련 이슈

Closes #142

## 변경 내용

- 날짜 조건을 함수 호출에서 범위 비교(`>= start AND < end`)로 변경
  -> 인덱스 활용 가능
- 종료일이 NULL인 경우 현재 시점까지로 처리하는 분기 추가

## 검증

- 기간별 조회 단위 테스트 추가 (경계값: 월말·연말·종료일 NULL)
- 레거시 통계와 12개월치 결과 대조하여 값 일치 확인

## 영향 범위

약품 통계 전체 메뉴. 날짜 조건을 공유하는 쿼리가 여러 화면에서 쓰이므로,
기간별·월계·일계 탭을 함께 확인해 주시면 좋겠습니다.
```

각 축이 드러나는 방식:
- **performance**: 타입으로 명시 + 인덱스 미활용 원인과 개선 결과를 서술
- **correctness**: NULL 분기 처리와 경계값 테스트 명시
- **test_coverage**: 단위 테스트 추가 + 대조 검증 방법 기술

---

## 사용자와의 상호작용

1. **먼저 생성해서 보여준다.** 질문부터 하지 않는다. 커밋 메시지와 PR body를 함께 제시한다.
2. 아래에 **어떤 근거로 각 항목을 넣었는지** 1~2줄로 짧게 설명한다.
3. diff만으로 알 수 없는 것은 **그때 묻는다.**
   - 이슈 번호를 못 찾았으면: "관련 이슈 번호가 있나요?"
   - 배경이 불명확하면: "이 수정 전에는 어떤 증상이 있었나요?"
   - 난이도 맥락: "기존 소스를 역추적하셨나요? 그렇다면 PR body에 넣으면 좋습니다."
4. 근거 없는 내용 추가 요청은 이유를 설명하고 대안을 제시한다.
   - 테스트를 안 썼는데 test_coverage를 채우고 싶어 하면
     → "테스트 코드는 없지만 수동 검증을 하셨다면 '검증' 항목에 그 방법을 쓰는 게 정확합니다."

## 커밋 분리 제안

팀 규칙이 **"한 커밋에는 한 가지 작업만"**이므로, 아래에 해당하면 반드시 분리를 제안한다.

- 기능 추가와 버그 수정이 섞임
- 리팩터링과 동작 변경이 섞임
- 서로 다른 모듈의 무관한 변경이 함께 있음

분리할 커밋 단위와 각각의 메시지를 함께 제시한다.
사용자가 한 번에 가겠다고 하면 그에 맞춰 작성하되, 주된 작업을 타입으로 삼는다.

# /database — 읽기 전용 DB 분석

프로젝트 코드와 실제 데이터베이스를 함께 읽어서, 스키마를 파악하고 질문에 답하고 필요하면 쿼리를 작성한다.

**이 스킬은 아무것도 바꾸지 않는다.** DB도, 프로젝트 파일도.

## 왜 이 제약이 중요한가

사용자는 같은 프로젝트의 코드를 **동시에 따로 작업하고 있다.** 그리고 연결 대상은 운영 DB일 수 있다.

그래서 세 방향으로 흔적을 남기면 안 된다:

| 경계 | 어기면 생기는 일 |
|---|---|
| **DB 쓰기 금지** | 데이터 손상. 되돌릴 수 없음. |
| **프로젝트 파일 수정 금지** | 사용자가 편집 중인 파일과 충돌. 작업 유실. |
| **운영 DB 부하/락 금지** | 조회만 해도 서비스 장애를 낼 수 있음. |

세 번째가 특히 놓치기 쉽다. `SELECT`는 "안전한 명령"이 아니다. 인덱스 없는 1억 행 테이블 풀스캔은 쓰기 작업만큼 위험하다.

---

## 절대 하지 않는 것

### DB에 대해

`INSERT` `UPDATE` `DELETE` `MERGE` `UPSERT` `TRUNCATE` `CREATE` `ALTER` `DROP` `RENAME` `GRANT` `REVOKE` `SET`(세션 안전 설정 제외) — **작성은 해줄 수 있어도 실행은 하지 않는다.**

덜 뻔하지만 똑같이 금지인 것들:

- `EXPLAIN ANALYZE` — 이름과 달리 **쿼리를 실제로 실행한다.** 계획만 볼 거면 `EXPLAIN`(ANALYZE 없이).
- `SELECT ... FOR UPDATE` / `FOR SHARE` / `LOCK TABLE` — 행 잠금이 걸린다.
- `VACUUM` `ANALYZE` `OPTIMIZE TABLE` `REINDEX` — 유지보수 명령. 무거운 락.
- `pg_terminate_backend` `KILL` — 남의 세션을 죽인다.
- `pg_dump` / `mysqldump` 전체 덤프 — 운영 DB에 대고 하지 않는다.
- 임시 테이블 생성(`CREATE TEMP TABLE`) — 쓰기다. 하지 않는다.

### 프로젝트에 대해

- 프로젝트 파일을 **읽기만** 한다. 수정·생성·삭제하지 않는다.
- `.env`, 설정 파일에 접속 정보를 **쓰지 않는다.**
- ORM/마이그레이션 CLI를 실행하지 않는다. 특히 위험한 것들:
  - `prisma migrate` `prisma db push` — 스키마를 실제로 바꾼다
  - `prisma db pull` — `schema.prisma` **파일을 덮어쓴다**
  - `alembic upgrade` `rails db:migrate` `typeorm schema:sync` `flyway migrate` — 전부 DDL 실행
  - `sequelize db:migrate`, `knex migrate:latest` 등도 동일
- 분석 결과물을 남길 일이 있으면 프로젝트 밖(예: `/tmp` 또는 사용자가 지정한 폴더)에 저장하고, 위치를 알려준다.

### 사용자가 쓰기를 요청하면

거부하지 말고, **실행만 하지 않는다.** SQL을 작성해서 보여주고 이렇게 전달한다:

> 이 스킬은 실행하지 않으니, 검토 후 직접 돌려주세요. 실행 전 백업과 트랜잭션 확인 권장합니다.

영향 범위를 미리 보여주면 좋다 — `UPDATE`를 만들었으면 같은 `WHERE`의 `SELECT COUNT(*)`로 몇 행이 영향받는지 함께 제시한다.

## 워크플로우

### 1단계 — 프로젝트 컨텍스트 파악 (읽기만)

DB에 붙기 전에 코드부터 본다. 스키마의 의도는 코드에 적혀 있고, 이걸 먼저 보면 질문의 절반은 DB 조회 없이 답이 나온다.

찾아볼 것:

- **DBMS 종류 힌트**: `package.json` / `requirements.txt` / `pom.xml` / `build.gradle` / `go.mod` / `Gemfile`의 드라이버 (`pg`, `mysql2`, `psycopg2`, `sqlite3`, `mongoose`, `oracledb`, `mssql` …)
- **스키마 정의**: `schema.prisma`, `models/`, `entity/`, `migrations/`, `*.sql`, JPA `@Entity`, Django `models.py`
- **접속 설정 형태**: `.env.example`, `application.yml`, `docker-compose.yml`, `database.yml` — **값이 아니라 구조만** 참고 (실제 `.env`의 비밀번호를 읽어서 화면에 뿌리지 않는다)
- **기존 쿼리**: 리포지토리 레이어, raw SQL

파악한 DBMS 종류를 사용자에게 확인받는다. 코드에 여러 드라이버가 있거나 못 찾겠으면 추측하지 말고 묻는다.

### 2단계 — 접속 정보 수집

**매번 물어본다. 저장하지 않는다.** 이전 대화에서 본 값을 재사용하지 않는다.

선택형으로 물을 수 있는 것은 `ask_user_input` 같은 도구로 묻고, 나머지는 직접 입력받는다. 필수 항목:

| 항목 | 왜 필요한가 |
|---|---|
| DBMS 종류·버전 | 문법과 시스템 카탈로그가 전부 다름 |
| host / port | — |
| database 이름 | — |
| user / password | — |
| **환경 (운영 / 스테이징 / 로컬)** | **가장 중요.** 운영이면 안전 수칙을 최대로 올린다 |
| 계정이 읽기 전용인지 | 읽기 전용 계정이면 사고 가능성이 구조적으로 사라짐 |
| 리드 레플리카 유무 | 있으면 무조건 레플리카로 붙는다 |
| 스키마/네임스페이스 | Postgres `search_path`, Oracle 스키마 등 |
| SSL / SSH 터널 필요 여부 | 접속 실패 원인 1순위 |

**운영 DB인데 계정이 읽기 전용이 아니라면**, 접속하기 전에 한 번 짚어준다:

> 운영 DB에 쓰기 권한 있는 계정이네요. 이 스킬은 조회만 하지만, 읽기 전용 계정을 따로 만들어 쓰시는 걸 권합니다. 이대로 진행할까요?

**비밀번호 취급:**

- 명령줄 인자로 넣지 않는다 (`ps`에 노출되고 셸 히스토리에 남는다). 환경변수나 옵션 파일을 쓴다.
- 응답·로그·파일에 다시 출력하지 않는다. 마스킹한다.
- 세션이 끝나면 어디에도 남기지 않는다.

### 3단계 — 안전하게 연결

DBMS별 구체적인 연결 문자열·안전 설정은 해당 참고 문서를 읽는다:

- PostgreSQL → `references/postgres.md`
- MySQL / MariaDB → `references/mysql.md`
- SQLite → `references/sqlite.md`
- Oracle / SQL Server / MongoDB 등 → `references/others.md`

공통 원칙은 셋이다:

1. **세션을 읽기 전용으로 고정한다.** 실수로 쓰기 쿼리를 날려도 DB가 막아준다.
2. **statement timeout을 건다.** 기본 5~15초. 폭주하는 쿼리가 서비스를 잡아먹는 걸 막는다.
3. **lock timeout을 짧게 건다.** 락을 기다리며 뒤에 줄 세우지 않는다.

연결이 되면 붙은 곳을 확인해서 사용자에게 알린다 — 호스트, DB명, 계정, 그리고 **읽기 전용 세션이 걸렸는지**.

### 4단계 — 대상 테이블 찾기

**규모부터 확인한다.** 테이블이 몇 개인지 세본다 (DBMS별 쿼리는 참고 문서에).

- **50개 이하** — 전체 목록을 봐도 된다. 5단계로.
- **그 이상** — **목록을 나열하지 않는다.** 검색으로 좁힌다.

큰 DB에서 테이블 목록 전체를 뽑는 건 정보가 아니라 노이즈다. 수백 개 이름을 훑어도 원하는 걸 못 찾고, 컨텍스트만 소모하고, 이름이 비슷한 걸 잘못 집기 쉽다. 사용자가 이 스킬을 부른 이유가 보통 **"어디 있는지 모르겠다"**이므로, 탐색이 이 스킬의 핵심 작업이다.

좁히는 방법은 넷이고, 위에서부터 정확도가 높다:

**① 코드에서 출발한다 (가장 정확)**
ORM 매핑에 테이블명이 적혀 있다. JPA `@Table(name=...)`, Django `db_table`, SQLAlchemy `__tablename__`, Prisma `@@map`, TypeORM `@Entity('...')`, ActiveRecord `table_name`. 도메인 용어로 코드를 먼저 grep해서 엔티티를 찾고, 거기서 실제 테이블명을 얻은 뒤 카탈로그로 확인한다. 매핑이 없으면 명명 규칙(복수형, snake_case 변환)이 적용됐을 가능성이 크다.

**② 테이블명으로 검색한다**
카탈로그를 `LIKE`로 조회한다. 도메인 용어 하나만 쓰지 말고 **동의어를 같이** 넣는다 — 취소라면 `cancel`, `void`, `refund`, `revoke`, 회원이면 `user`, `member`, `account`, `customer`. 한국어 서비스는 영어 약어(`mbr`, `ord`, `pay`)나 로마자 표기가 섞이기도 한다.
샘플 몇 개를 뽑아 **명명 규칙을 먼저 파악**하면 검색이 훨씬 정확해진다 — 접두사(`tb_`, `t_`, 모듈명), 단수/복수, 구분자.

**③ 컬럼명으로 역추출한다**
테이블명이 도메인 용어와 안 맞을 때 쓴다. `canceled_at`, `refund_amount` 같은 컬럼을 가진 테이블을 카탈로그에서 찾는다. 테이블 이름이 `t_ord_hist` 같은 약어라 검색에 안 걸릴 때 이 방법이 유일한 길이다.

**④ 외래키로 확장한다**
기준 테이블 하나가 확정되면, 거기서 나가고 들어오는 외래키를 따라 **1~2 홉까지만** 넓힌다. 관련 테이블 대부분이 여기서 나온다. 무한정 확장하지 말고, 홉마다 관련성을 판단한다.

**후보가 여러 개면 사용자에게 확인받는다.** 추측으로 하나 골라서 분석을 쭉 진행하지 않는다. 후보별로 행 수 추정치와 주요 컬럼을 짧게 보여주고 어느 쪽인지 묻는다.

**비슷한 이름 함정에 주의한다.** `orders`, `orders_old`, `orders_bak`, `tmp_orders`, `orders_2019`가 함께 있는 건 흔하다. 실제로 쓰이는 게 무엇인지는 이렇게 가른다:

- 코드가 참조하는 이름이 무엇인가 (가장 확실한 근거)
- 최근 데이터가 들어오고 있는가 — `SELECT max(created_at)` 같은 걸로 확인 (인덱스 있는 컬럼일 때만)
- 행 수 추정치와 크기가 현재 트래픽과 맞는가

판단 근거를 응답에 같이 적는다. "이 테이블로 보입니다"가 아니라 "코드 A가 이 이름을 참조하고, 최근 데이터도 여기 쌓입니다"라고 쓴다.

### 5단계 — 스키마 확정

**4단계에서 좁혀진 테이블에 대해서만** 구조를 본다. 시스템 카탈로그 조회는 가볍고 락도 걸지 않는다.

1. 컬럼·타입·NULL 여부·기본값·코멘트
2. 인덱스 — 조인·필터 설계의 근거
3. 제약조건·외래키 — 조인 경로
4. 필요하면 뷰·트리거 (뷰인 줄 모르고 테이블로 다루면 성능 판단이 어긋난다)
5. **행 수는 통계 기반 추정치로 먼저 본다.** 대형 테이블에 `SELECT COUNT(*)`를 때리는 것 자체가 부하다. 정확한 수가 꼭 필요할 때만, 그것도 크기를 확인한 뒤에 실행한다.

컬럼 코멘트가 달려 있으면 꼭 읽는다. 광범위한 DB일수록 이름만으로는 의미를 알 수 없는 컬럼(`status`가 뭘 뜻하는지, `type`이 어떤 값을 갖는지)이 많다. 코멘트가 없으면 **실제 값의 분포**를 좁은 범위에서 확인해 의미를 추론한다.

### 6단계 — 데이터 조회

부하 관리가 이 단계의 전부다:

- **항상 `LIMIT`을 붙인다.** 샘플은 기본 20~100행. `LIMIT` 없는 조회는 하지 않는다.
- **`SELECT *` 대신 필요한 컬럼만.** 특히 `TEXT`/`BLOB`/`JSON` 컬럼은 무겁다.
- **큰 테이블은 실행 전 `EXPLAIN`으로 계획을 본다.** 풀스캔이 잡히면 멈추고 사용자에게 알린 뒤 조건을 다시 잡는다.
- **집계는 범위를 좁혀서.** 전체 기간 `GROUP BY`보다 최근 N일로 시작한다.
- **결과가 크면 요약해서 보고한다.** 수천 행을 화면에 쏟지 않는다.
- **운영 DB에서 무거운 쿼리(수 초 이상 예상)는 실행 전에 사용자 승인을 받는다.**

민감 데이터(비밀번호 해시, 주민번호, 카드번호, 토큰)는 조회 대상에서 빼거나, 값 대신 존재 여부·형식만 확인한다. 응답에 원본을 그대로 싣지 않는다.

### 7단계 — 쿼리 작성

요청받으면 SELECT 쿼리를 작성한다. 작성할 때:

- 스키마를 확인하고 쓴다. 컬럼 이름을 추측하지 않는다.
- 인덱스를 보고 조인·필터 순서를 정한다.
- `EXPLAIN`으로 계획을 확인해서 근거와 함께 제시한다.
- 애플리케이션에 넣을 쿼리면 **파라미터 바인딩** 형태로 준다. 문자열 붙이기는 SQL 인젝션이다.

## 보고 형식

분석 결과는 이 순서로 전달한다:

```
## 접속 정보
호스트 / DB / 계정 / 환경 / 읽기 전용 세션 여부

## 찾은 테이블
어떤 테이블을 봤고, 그게 맞다고 판단한 근거 (코드 참조 / 컬럼 구성 / 최근 데이터)
※ 테이블을 찾는 게 목적이 아니었으면 생략

## 실행한 쿼리
답을 얻기 위해 돌린 쿼리 전문. 사용자가 그대로 재실행·수정할 수 있게.

## 결과
발견한 내용. 표가 도움이 되면 표로.

## 코드와의 관계
프로젝트 코드의 어느 부분이 이 스키마와 대응하는지 (파일:라인)

## 참고
성능·정합성·설계상 눈에 띈 점. 확인된 것만 쓴다.
```

추측과 확인된 사실을 섞지 않는다. 조회로 확인한 것과 코드에서 읽은 것과 추정을 구분해서 쓴다.

## 자주 마주치는 상황

**접속이 안 된다**
연결 정보를 재확인하고, SSL/터널 필요 여부를 묻는다. 방화벽/화이트리스트 문제일 수 있다. **프로젝트의 설정 파일을 고쳐서 뚫으려 하지 않는다.**

**권한이 부족하다**
어떤 권한이 왜 필요한지 설명하고 사용자에게 요청한다. 다른 계정을 찾아 쓰거나 권한을 스스로 올리지 않는다.

**"이 테이블 크기가 궁금해"**
통계 기반 추정치와 디스크 사용량으로 답한다. `COUNT(*)` 전에 이것부터.

**"느린 쿼리 좀 봐줘"**
`EXPLAIN`(ANALYZE 없이) + 인덱스 정보 + 테이블 통계로 분석한다. 실측이 꼭 필요하면 **스테이징에서 하도록** 안내한다.

**"이 데이터 어느 테이블에 있는지 찾아줘"**
이 스킬의 주된 용도다. 4단계 탐색으로 간다. 코드 → 테이블명 → 컬럼명 → 외래키 순으로 좁히고, 근거와 함께 후보를 제시한다.

**검색해도 후보가 안 나온다**
포기하기 전에 이것들을 확인한다 — 스키마/네임스페이스가 여러 개인가(`public` 밖에 있을 수 있다), 대소문자 구분 문제인가, 도메인 용어와 다른 약어를 쓰는가, 별도 DB나 다른 서버에 있는가. 그래도 안 나오면 추측하지 말고 사용자에게 아는 단서(화면 이름, API 경로, 로그의 필드명)를 묻는다.

**대화 중간에 다른 DB로 옮겨간다**
2단계로 돌아가 접속 정보를 처음부터 다시 받는다. 이전 연결 정보를 섞지 않는다.

# /test — 개발 후 검증 & 수동 테스트 체크리스트 생성

개발이 끝난 뒤 실행하는 스킬. **현재 작업 중인 프로젝트**(스킬이 실행되는 곳)를 대상으로:

1. 코드를 정적분석하고
2. 프로젝트를 빌드해 오류 0을 확인한 뒤
3. 사용자가 프로그램을 직접 실행하며 확인해야 할 **수동 검증 체크리스트**를 만들어 준다.

프로젝트는 매번 다를 수 있다. 이 스킬은 특정 언어/프레임워크에 종속되지 않으며, **실행되는 프로젝트의 지침과 구조를 먼저 파악한 뒤** 그에 맞춰 동작한다.

---

## 핵심 원칙

- **분석 범위는 현재 프로젝트 전체.** 어떤 프로젝트에서 실행되든 그 프로젝트를 분석한다.
- **버그·빌드 오류는 보고만 한다.** 발견한 문제는 목록으로 정리해 보고하고, **사용자 승인을 받은 뒤에만 수정**한다. 승인 없이 코드를 고치지 않는다.
- **프로젝트 지침을 최우선으로 따른다.** 빌드 방법, 인코딩 규칙, 편집 제약 등은 프로젝트 지침(CLAUDE.md/AGENTS.md 등)이 있으면 그대로 따르고, 없으면 자동 감지한다.
- **체크리스트는 "사용자가 직접 실행해 확인할 것" 중심.** 자동 분석/빌드로 이미 검증되는 항목이 아니라, 사람이 프로그램을 돌려 눈으로 확인해야 하는 행동·시나리오를 담는다.
- **출력 파일은 덮어쓰기.** `테스트_체크리스트.md` 하나를 항상 갱신한다. 인코딩은 UTF-8.

---

## 실행 순서

### 1단계 — 프로젝트 파악 (지침 → 감지 순)

먼저 프로젝트를 이해한다.

1. **프로젝트 지침 읽기**: `CLAUDE.md`, `AGENTS.md`, `README`, `.claude/` 등을 확인한다. 여기에 아래가 있으면 반드시 따른다.
   - 빌드/실행/검증 명령
   - 인코딩 규칙(예: 특정 파일은 CP949 유지, 임의 재저장 금지)
   - 편집 제약(예: 특정 도구 사용 금지, 특정 방식으로만 저장)
   - 변경 금지 범위, 승인 규칙
2. **프로젝트 종류 감지**: 지침에 빌드 방법이 없으면 매니페스트/설정 파일로 종류를 판별한다.

   | 감지 근거 | 종류 | 빌드/검증 예 |
   |---|---|---|
   | `*.dproj`, `*.dpr` | Delphi | `rsvars.bat` 후 `msbuild <proj>.dproj /p:Config=Debug /p:Platform=Win32` |
   | `package.json` | Node/JS/TS | `npm run build` / `npm run typecheck` / `npm run lint` |
   | `*.csproj`, `*.sln` | .NET | `dotnet build` |
   | `pyproject.toml`, `setup.py` | Python | `ruff`/`mypy`/`python -m compileall` |
   | `Cargo.toml` | Rust | `cargo build` / `cargo clippy` |
   | `go.mod` | Go | `go build ./...` / `go vet ./...` |
   | `pom.xml`, `build.gradle` | Java | `mvn compile` / `gradle build` |
   | `Makefile` | 기타 | `make` |

   목록에 없거나 빌드 수단을 못 찾으면 **정적분석만 진행**하고, 빌드를 건너뛴 사실을 결과에 경고로 표시한다.

### 2단계 — 정적분석

프로젝트 코드를 읽고 문제를 찾는다.

- **범위**: 현재 프로젝트 전체. 변경분(작업 브랜치의 `git diff`, 최근 커밋, 미커밋 변경)이 있으면 그 부분을 **우선**으로 더 깊게 본다.
- **찾을 것**: 명백한 버그, 논리 오류, 누락된 조건(WHERE/날짜/필터/삭제여부 등), 집계·계산식 오류, null/경계 처리, 자원 누수, 예외 미처리 등.
- **결과는 보고만.** 심각도(높음/중간/낮음)와 `파일:라인`, 근거, 제안 수정 방향을 정리한다. **이 시점에 코드를 고치지 않는다.**

### 3단계 — 빌드 (오류 0 확인)

1단계에서 정한 방법으로 빌드한다.

- **빌드 성공(오류 0)**: 통과로 기록.
- **빌드 실패**: 오류 메시지를 그대로 캡처해 보고한다. **자동으로 고치지 않는다.** 2단계 정적분석 결과와 함께 문제 목록에 포함한다.
- 프로젝트에 별도 검증(typecheck/lint/test)이 정의돼 있으면 함께 실행하고 결과를 기록한다.

### 4단계 — 발견 문제 보고 & 승인

2·3단계에서 나온 문제를 하나의 목록으로 사용자에게 보고한다.

- 각 항목: 심각도 · `파일:라인` · 증상 · 제안
- 그런 다음 **"어떤 항목을 수정할까요?"**를 물어, **승인받은 항목만 수정**한다.
- 수정 시에도 1단계에서 확인한 프로젝트의 인코딩·편집 규칙을 반드시 지킨다.
- 수정 후에는 다시 빌드해 오류 0을 확인한다.

### 5단계 — 수동 검증 체크리스트 생성

`테스트_체크리스트.md`를 **UTF-8**로, **덮어쓰기**로 작성한다.

- **성격**: 사용자가 프로그램을 직접 실행하며 확인할 행동·시나리오 중심. (정적분석/빌드로 이미 자동 검증된 것은 넣지 않는다.)
- **구성**: 기능/화면/모듈 단위로 그룹화하고, 각 항목은 체크박스(`- [ ]`)로.
- **변경 영역 강조**: 이번 작업으로 바뀐 부분은 눈에 띄게 표시(예: 🔧)해 우선 확인하도록 한다.
- **주의 표시**: 데이터가 없거나 전제 조건이 필요한 항목은 경고(예: ⚠️)로 표시한다.
- **머리말**: 대상/검증 방법/빌드 결과/인코딩 등 전제를 문서 상단에 요약한다.

#### 템플릿

```markdown
# <프로젝트명> 검증 체크리스트

- 대상: <이번 검증 범위 / 제외 항목>
- 방법: 프로그램을 직접 실행하며 <진입 → 조건 설정 → 실행 → 결과 확인>
- 빌드: <빌드 명령> 오류 0 확인 (<날짜>)
- 인코딩: <프로젝트 인코딩 규칙 요약>
- 표기: [ ] 실기 테스트 대상 / 🔧 이번 수정 반영(우선 확인) / ⚠️ 데이터·조건 주의

---

## 1. <기능/화면/모듈>

- [ ] <사용자가 직접 확인할 행동/시나리오와 기대 결과>
- [ ] 🔧 <이번에 바뀐 부분 — 우선 확인>
- [ ] ⚠️ <데이터·전제 조건 주의가 필요한 항목>

## 2. <다음 기능/화면/모듈>

- [ ] ...

---

## 부록 A. 이번 수정 완료 항목
| 모듈 | 수정 내용 |
|---|---|
| ... | ... |

## 부록 B. 미구현 · 보류
- ...
```

## 완료 보고

작업을 마치면 다음을 사용자에게 요약한다.

- 정적분석 결과(문제 수 / 심각도별)
- 빌드 결과(성공/실패, 오류 수)
- 승인받아 수정한 항목
- 생성/갱신한 파일: `테스트_체크리스트.md`
- 남은 리스크 / 실행하지 못한 검증과 이유

---

## 주의

- 이 스킬은 **개발 완료 후 검증** 용도다. 승인 없이 리팩터링·대량 포맷팅·기능 변경을 하지 않는다.
- 프로젝트 지침과 이 스킬의 기본 동작이 충돌하면 **프로젝트 지침을 우선**한다.
- 한글·인코딩이 걸린 파일을 다룰 때는 프로젝트 지침의 인코딩 규칙을 반드시 확인하고, 불명확하면 먼저 질문한다.
